## 已确认的决策

1. 采用 Qwen3.5-0.8B **全量微调**。训练的是候选匹配判断，模型不生成 JSON 字符串；本地服务负责组装 JSON。
2. 输入字段与 Jev 的 HTTP 接口对应：`model`、`state`、`questions`。支持 `choice`、`score`、`noul`。
3. 按用户后续要求，输出删除 `confidence`。其余响应字段按下文约定。因此是 **Jev 格式去掉 confidence 的兼容变体**，不是官方响应逐字段完全复刻。

5. **保留 probabilities 与 noul 概率**。不需要置信度不等于删除概率；Choice/Score 的概率用于监督学习和派生最终选择/分数。
6. 500 题覆盖 50 个领域，每领域 10 题。其中 **25 题情感分类、25 题意图识别**，分布于 25 个领域，对应各 250 条请求；另有 450 题综合判断。清单的 `task_family` 标识专项类型，不进入接口或模型输入。每题所有场景只进入一个数据集合；划分已固化在清单，agent 不自行修改。
7. 命题、计划、脚本和环境已就绪；每个 subagent 负责两个领域，详见 `docs/4、实际生成执行说明.md`。**500 题已于 2026-09-21 全部生成完毕并通过全量校验**（5,000 条请求、6,000 个问题，划分 4000/500/500）。不能把示例或程序测试样本计入 5,000 条。
8. 训练和新训练断点的推理输入上限均为 **8,192 token**，按每个候选实际编码后的完整输入计数，超长报错，不静默截断。后续新生成数据采用更短的固定分布：**每题9短1中，短≤512 token，中513—1,024 token**；此为数据生成约束。

## 接口依据与边界

核对日期：2026-09-21。参考官方 [接口文档](https://docs.typesafe.ai/api)、[Choice](https://docs.typesafe.ai/primitives/choice)、[Score](https://docs.typesafe.ai/primitives/score)、[Noul](https://docs.typesafe.ai/primitives/noul) 和 [介绍](https://docs.typesafe.ai/introduction)。本项目自行实现训练方式，不声称复制 Jev 的专有模型、速度、概率校准或决策水平。

机器可读字段规范位于 `schemas/request.schema.json` 与 `schemas/response.schema.json`；概率总和、分数计算和问题 ID 对应等关联约束由校验脚本额外检查。

### 请求格式

```json
{
  "model": "jev-latest",
  "state": {"反馈": "发来的鞋尺码错了，请换成下单的尺码。", "状态": "已签收"},
  "questions": {
    "处理部门": {
      "type": "choice",
      "instructions": "哪个部门最适合处理当前诉求？",
      "criteria": {"售后": "退货、换货、错发", "物流": "派送与在途", "财务": "支付和发票"}
    },
    "诉求完整度": {
      "type": "score",
      "instructions": "只评价是否说明问题和期望处理方式。",
      "criteria": ["未说明问题", "说明问题但未明确处理方式", "问题和期望处理方式均明确"]
    },
    "要换货": {"type": "noul", "instructions": "客户是否明确要求换货？"}
  }
}
```

`state` 和 `instructions` 可为字符串、对象或数组。Choice 的 `criteria` 是选项名到描述的对象，选项描述支持字符串、对象、数组或 `null`；通常写清楚中文描述。Score 的 `criteria` 是有序数组，2—10 个等级，每级均需有独立可理解的含义。Noul 可省略 `criteria`，也可给出 `true`、`false` 的定义。JSON 里的这两个键是英文字符串，不能写成中文键或布尔键。

问题 ID 仅用于对应答案，**不传给底层模型**；不能使用“应选售后”“答案为真”这样的 ID 暗示标签。每个问题只依赖自己的说明和同一 `state`，不能引用另一个问题的答案。

### 响应规则

- Choice：`{"type":"choice","choice":"选项名","probabilities":{"选项名":0.9,"其他选项":0.1}}`。覆盖所有选项，概率和为 1，choice 取最大概率的选项。
- Score：`{"type":"score","score":1.7,"legend":{"0":"低","1":"中","2":"高"},"probabilities":{"0":0.0,"1":0.3,"2":0.7}}`。下标从 **0** 开始，score 为 `Σ(i × p_i)`，范围是 `0…等级数-1`，不是固定 0—1，也不是最高概率下标。
- Noul：`{"type":"noul","noul":0.97}`。noul 是命题成立的概率，不是事情的严重程度。
- 外层统一为 `{"model":"openjev-qwen3.5-0.8b-v1","answers":{...},"usage":{"input_tokens":0,"output_tokens":0}}`。
- 任意层不得增加 `confidence`、`reasoning`、`rationale` 或 `think` 响应字段。简短标注依据只进入样本外层 `review.evidence`。
- `legend` 的字符串等级保留原文；对象/数组等级在本地实现中序列化为紧凑 JSON 字符串。官方文档允许结构化等级但声明 legend 为字符串映射，本项目固定这个序列化约定。
- Choice 并列最大时，本地工具取请求里先出现的选项。这是确定性的边界处理，不表示该选项更有依据。
- 草稿转正式样本时 `usage` 为 0，是未执行模型的占位计数；不参与训练。真实推理计算实际编码 token 总量，包含重复处理的状态；由于不生成文本，`output_tokens=0`。这不是 Jev 的计费口径。

## 每题 10 条的固定构成

| 槽位 | 类型 | 场景要求 | review.case_type |
|---|---|---|---|
| 01 | Choice | 信息清楚，明确匹配一个类别 | 明确匹配 |
| 02 | Choice | 两个类别容易混淆，但存在区分线索 | 易混类别 |
| 03 | Choice | 核心事实缺失或确实存在歧义 | 信息不足 |
| 04 | Choice | 否定、纠正、引用或无关干扰；仍只问一个维度 | 否定或干扰 |
| 05 | Score | 明确符合较低等级 | 低等级 |
| 06 | Score | 中间等级，或相邻等级边界 | 中间或边界等级 |
| 07 | Score | 明确符合较高等级 | 高等级 |
| 08 | Noul | 有直接证据支持肯定 | 明确肯定 |
| 09 | Noul | 有直接证据支持否定；不能只是没提到 | 明确否定 |
| 10 | 混合 | 同一新状态下恰好 1 Choice + 1 Score + 1 Noul | 混合独立问题 |

全量计数：Choice 2,500 问，Score 2,000 问，Noul 1,500 问，总计 6,000 问。槽位 10 的 Noul 中，每组应至少 5 题体现证据不足；不要求所有混合样本都给确定答案。

**十条应有实质变化**：事实组合、表达方式、任务边界和噪声至少变化两项。不能只替换姓名、金额或商品名。反事实样本可以保留相似结构，但必须改变决定标签的关键事实，并说明改变在哪里。

### 语言与长度

- 所有命题、状态叙述、问题说明和描述性标签以中文为主；结构字段名按 schema 使用英文，专有型号、代码和原始日志可保留。
- 短场景使用简洁、自包含的状态；中等场景可使用多轮对话、工单历史、规则与记录组合。中文字符数不能替代 token 实测，每个问题尽量只问一个维度。
- 说明建议不超过 80 字；每个候选描述一般 10—45 字。训练通常使用 2—6 个 Choice 选项、3—5 个 Score 等级。
- 每题至少 1 条结构化 state；每组至少 5 条数组 state、5 条结构化 instructions、5 个结构化候选描述。可用订单、日志、对话记录等，不为凑格式牺牲语义。
- 每个候选的完整编码输入（任务前缀、JSON 结构、state、单个问题的 type / instructions、单个候选描述和判断后缀）必须 **≤8,192 token**。按本地 Qwen tokenizer 测量；不是字符数，也不是仅限制 state。一个请求有多个问题时，每个候选分别满足限制，`usage.input_tokens` 的累计值可以超过 8,192。
- **后续新生成的每题10条必须恰好9条短输入（≤512 token）和1条中等输入（513—1,024 token）**，不生成超过1,024 token的样本。512 token归短，1,024 token归中，两个区间不重叠。按一个请求中所有问题、所有候选的最长完整编码输入归档，不能按字符数、state长度或累计usage归档。中等样本所在槽位可在题目间轮换，十个题型槽位不变；混合槽位仍只计一条请求。
- 中等样本的关键证据可位于开头、中段或末尾，使用有意义的引用、改口或关联记录形成自然长度。超过所属区间时压缩重复内容并重新测量，不机械填充，不截断关键事实。T0001—T0060共600条为旧方案产物，按用户明确要求保持原样，不按新规则重做；不得宣称它们已满足新比例。T0061—T0500已按新比例生成完毕，全库检查见 `reports/generation/进度.md`。
- Choice 支持最多 255 选项，但此训练集主要覆盖少量候选；不能把协议支持理解为已验证 255 选项场景的质量或速度。

### 情感分类和意图识别的专项要求

专项命题仍遵守相同的 10 个槽位和 Choice / Score / Noul 接口，不增加情感或意图专用字段。每题的十条都围绕该专项构造，不能仅用一条分类样本，其余转为无关业务判断。

**情感分类：** 在问题中明确“谁对什么、在哪个时间段表达何种情感”。Choice 可以使用正面、负面、混合、中性、信息不足，或使用喜悦、担忧、愤怒等细分类别；同一问题的类别需互斥且说明边界。真实褒贬混合与无法确定态度应分开，中性与完全缺少证据也应分开。Score 只衡量一个有序维度，例如不满程度从无明显不满到强烈不满，不把喜悦、愤怒、悲伤排列成高低等级。Noul 问一个原子命题，例如“发言者是否明确表示满意”。

情感样本至少覆盖明确态度、委婉表达、反讽或否定、引用他人态度、混合评价和证据不足。不能凭感叹号、身份、事件严重性推断情绪，不将情感标签写成心理健康诊断。槽位 09 的否定要有明确反证，例如“服务我很满意，只是想查进度”，而非单纯没有抱怨。

**意图识别：** 明确目标说话者和当前有效诉求，区分表达情绪、询问条件、计划尝试、正式提出请求和已完成的动作。Choice 分类主意图；多意图时在 instructions 写清“最近一次明确请求”等选择规则，或提供互斥的组合类别，不能擅自忽略次要诉求。若要判断多个意图是否存在，分别使用独立 Noul 问题；本计划固定槽位不随之增加问题数，可分到不同场景。Score 可衡量请求的明确程度或信息完整度，不能给退货、换货、维修等无序意图编号后当连续分数。

意图样本至少覆盖直接请求、委婉请求、否定与取消、多轮改口、多意图及信息不足。区分“能退吗”和“请帮我退”；区分“朋友说他要取消”和说话者本人要求取消。槽位 10 同时评估当前意图、诉求明确程度和一个具体意图命题，三个问题均直接依据 state。

示例边界：“质量不错，但客服让我很失望。先别退款，换一件就行。”若问题针对客服情感，应判负面；针对当前处理意图，应判换货；“是否要求现在退款”应判否定。此示例只用于理解规则，不能复制充当正式训练数据。

## 标签如何生成

### 先事实，再问题，再标签

1. 阅读命题简介，确定一个可由所给状态判断的原子维度。
2. 构造具体、可信、自包含的虚构场景。涉及政策、合同、医学流程和技术规范时，将判断所需规则写在状态或问题中；不依赖 agent 臆测现实法规或专业结论。
3. 为 Choice 写互斥且可区分的候选；必要时提供“其他”或“信息不足”，不要强制所有场景落入不合适的类别。Score 等级需要有序且清楚，不能仅写“1、2、3”。
4. 在不查看预设目标类别的情况下复核事实所支持的答案。不得先决定高分再拼凑完全一样的关键词场景。
5. 在 `review.evidence` 中为每个问题写一两句话，指向关键事实和对应规则；这是简短可核查依据，不要求隐藏推理过程。
6. 最后标注概率，避免“信息不足却总是 0.99”的模式。

### 概率是软标签，不是校准承诺

本次不调用 Jev 教师服务。标签来源必须标记 `agent_synthetic`。agent 的概率代表标注偏好和不确定性，不能当作经过真实频率校准的概率。

- 明确事实可以给较集中的分布，例如 `[0.94,0.04,0.02]`；这些只是示例，不是每行套用的固定常数。
- 边界案例可把概率分配给相邻或易混的类别。Score 的非相邻双峰必须有可说明的证据，不能为了得到某个均值随便分配。
- 若有“信息不足”选项且确实缺证据，可以高概率选择它；若没有此选项，按合理候选给更分散分布。不能把“不足”自动当作事实为假。
- Noul 的肯定与否定样本需要分别有事实支持；混合槽位可用接近 0.5 表示无法判断。
- 不输出伪精确的小数，标注用 2—3 位小数通常足够。不要生成负数、百分数字符串、NaN 或 Infinity。
- 概率和必须为 1；派生的 choice、score、legend 由工具计算，agent 不手工心算这些冗余字段。

## 草稿 schema

UTF-8 无 BOM 的 JSONL，每行一条对象；以下为了阅读展示为多行，实际必须压成一行。

```json
{
  "sample_id": "T0001-01",
  "topic_id": "T0001",
  "slot": 1,
  "request": {
    "model": "jev-latest",
    "state": "我收到的鞋比订单尺码小两号。商品没有损坏，也不是要退款，请帮我换成订单上写的尺码。",
    "questions": {
      "诉求": {
        "type": "choice",
        "instructions": "客户当前明确希望怎样处理商品？",
        "criteria": {"退货退款": "退回商品并收回款项", "换货": "更换商品或规格", "维修": "修理现有商品", "仅咨询": "没有提出实际处理请求"}
      }
    }
  },
  "labels": {"诉求": {"probabilities": {"退货退款": 0.01, "换货": 0.97, "维修": 0.01, "仅咨询": 0.01}}},
  "review": {
    "case_type": "明确匹配",
    "evidence": {"诉求": "客户明确要求更换为订单尺码，并明确否定退款。"},
    "label_source": "agent_synthetic"
  }
}
```

Score 的 labels 用 `{"问题ID":{"probabilities":{"0":0.1,"1":0.7,"2":0.2}}}`；Noul 用 `{"问题ID":{"noul":0.95}}`。混合请求的 labels 包含全部三个问题。

执行下列工具后，正式样本用完整 `response` 替换 `labels`，保留其余元数据：

```powershell
.\.venv\Scripts\python.exe -m scripts.finalize_shard data/drafts/T0001.jsonl
```

工具要求 10 条完整槽位全部存在，验证成功后才发布到 `data/shards`。原文件已存在时不会覆盖。若校验失败，修改草稿后重试；不要绕过校验发布半个分片。

## 分组、派发与恢复

共 **20 组，每组 25 个命题、250 条请求**。第 g 组的编号范围为 `T{25(g-1)+1:04d}` 到 `T{25g:04d}`。组号已写在每条命题里。

- 一次任务只做指定组，完成后汇报并停止，等待用户启动下一组。
- 建议先做 T0001 的 10 条试生成，经语义审阅后继续第 1 组；样本合格便可保留，不需重复生成。
- 用户若允许子 agent，可以一个命题交给一个 worker，最多使用当前环境实际可用的并发数；每个 worker 只写自己的文件。没有并发工具时顺序完成即可。
- 不照搬参考计划里的 10 并发或不存在的 Workflow API。当前任务已写好资料，**没有启动 500 个 agent**。
- 已存在分片必须先通过格式与语义核验，不能仅因文件存在就跳过。损坏文件保留备份并修复，不静默删除。
- 某题失败只重跑该题。topic_id、slot、sample_id 是固定身份；不得重新编号补洞。
- 先本组校验，再全局查重；语义近似不能仅靠精确哈希发现，需要人工或独立复核。

给未来主 agent 的可直接使用指令：

> 请阅读 openjev 项目的 docs/1、决策训练数据生成计划.md，只完成第 N 组。读取 data/topics.jsonl 中 group=N 的 25 个命题，逐题生成 10 条独立中文决策请求。读取 task_family，情感分类和意图识别题遵守专项规范。严格使用固定槽位、草稿 schema 和标签规范；每题严格9条短输入（完整候选输入≤512 token）及1条中等输入（513—1,024 token），按请求最长候选归档。每题写入 data/drafts/Txxxx.jsonl，运行 finalize_shard 生成正式分片。不得生成 confidence，不得更改已固定的数据划分。已存在分片先校验再判断是否跳过。完成本组后运行 validate_data --group N 和 preflight_data；抽查语义，报告数量、长度覆盖、问题及失败编号，然后停止。500 题已生成完毕；此指令只在用户要求重做或补做某组时执行。

单个 worker 的任务指令：

> 只处理命题 Txxxx。先读计划及此命题的 title、brief、task_family，构造固定的 10 个槽位；遵守情感或意图专项规范，每题严格9短（≤512 token）1中（513—1,024 token），按请求最长完整候选输入归档。内容必须自包含、中文为主、状态足够支持标签，各场景有实质变化。只写自己命题的草稿文件，随后运行 finalize_shard 并修正校验错误。返回 topic_id、shard_path、sample_count、question_count、status、note。不生成其他命题，不改脚本，不运行正式训练。500 题已生成完毕；此指令只在用户要求重做或补做某题时执行。

返回摘要：`{"topic_id":"T0001","shard_path":"data/shards/T0001.jsonl","sample_count":10,"question_count":12,"status":"ok","note":""}`。

## 质量闸门

### 自动检查

```powershell
.\.venv\Scripts\python.exe -m scripts.validate_data --group 1
.\.venv\Scripts\python.exe -m scripts.preflight_data --group 1
# 全部 20 组完成后：
.\.venv\Scripts\python.exe -m scripts.validate_data --require-all
.\.venv\Scripts\python.exe -m scripts.prepare_data
.\.venv\Scripts\python.exe -m scripts.preflight_data --prepared
```

校验脚本检查：分片数、每题 10 条、槽位、ID、三类题型、概率范围与和、Score 期望值、legend、响应多余字段、跨集合精确重复和请求精确重复。长度预检使用本地 tokenizer，不需要模型权重下载完成，并逐题报告新方案9短1中的符合情况。对后续新生成的命题使用 `preflight_data --topics T0061 T0062 --enforce-mix`（替换为本批全部命题ID）；不符合比例或超过1,024 token即失败。旧方案数据默认仅报告差异，不自动改写。

### 必须做的语义复核

每组至少抽查 5 个完整命题（50 条，覆盖槽位 03、04、06、09、10），余下命题至少检查一个边界样本。抽查须回答：

1. 只凭状态和说明是否能支持标签？是否靠领域刻板印象或未提供的法规？
2. 候选是否互斥、描述是否清楚、Score 是否真的单一有序维度？
3. 明确否定与未提及是否区分？文本中的转述和恶意命令是否被误执行？
4. 概率是否与证据强弱匹配？选项顺序变化是否会无理由改变答案？
5. 十条是否只是换名字？是否存在跨题复制或训练/测试近似场景？
6. 请求是否夹带答案、review 或同批其他问题？

发现系统性问题，先修改该组同类问题，再扩大抽检。自动通过只说明结构合格，不代表语义正确。

## 集合划分与训练接入

每领域固定 8 题训练、1 题验证、1 题测试：400 / 50 / 50 个命题。得到 **4,000 / 500 / 500 条请求**，展开后是 **4,800 / 600 / 600 个问题**。

同一命题的全部 10 条和其反事实变体始终留在同一集合。这个测试衡量已覆盖领域中的未见命题泛化，不是未见领域测试。测试集不能参与调参、选断点或重写标签以迁就模型。

`prepare_data` 保留请求级记录供接口评估，并为训练展开独立问题。训练输入只有 `state`、问题 type、instructions 和单个候选描述；候选的完整概率分布作为组内监督目标。Score 不把等级序号作为语义输入；其顺序只用于组装 score。真实推理复用完全相同的输入构造。

在验证集选训练参数和断点，再一次性报告测试集的 Choice 选项一致率、Score 平均绝对误差、Noul 误差，以及对软标签的交叉熵。由于参照是合成标签，报告为“与标注一致程度”，不能写成真实业务准确率。

训练和本地使用命令见 `docs/3、本机全量微调与使用.md`。
